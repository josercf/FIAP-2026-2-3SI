PRD (Product Requirements Document) [1]

O PRD não é uma lista de funcionalidades: é o documento que responde por que estamos construindo isto e para quem. Ele descreve o problema, nunca a solução técnica.

O que todo PRD precisa ter

  • Visão e Problema: a dor real do mercado
  • Personas e Casos de Uso: quem usa e como
  • Requisitos Funcionais e Não Funcionais: verificáveis, com identificador
  • Métricas de Sucesso: como saberemos que deu certo

O que acontece sem ele

Sem PRD, cada desenvolvedor inventa a regra de negócio que falta. O resultado é retrabalho, débito técnico e a descoberta tardia de que o time construiu a coisa certa para o usuário errado.

PRD como contexto de IA: um PRD bem escrito vira o insumo que o modelo usa para gerar arquitetura e código coerentes. Lixo entra, lixo sai. Lab Kit da Aula 01

SDD: Spec Driven Development [2]

A engenharia de software sempre soube que especificar antes reduz risco (Pressman, Sommerville). O que mudou com a IA é que a especificação deixou de ser papel arquivado e virou a entrada executável do processo.

MODELO TRADICIONAL
Especificação escrita
↓
Código escrito à mão
↓
Spec vira documentação morta
SPEC DRIVEN DEVELOPMENT
Especificação é a fonte da verdade
↓
Plano técnico derivado dela
↓
Código gerado e regenerável

A inversão: no modelo antigo o código era o artefato valioso e a spec, um subproduto. No Spec Driven Development a spec é o ativo, e o código passa a ser sua expressão. Mudou o requisito? Muda-se a spec e regenera-se, em vez de remendar o código.

DDD: A Importância da Linguagem Ubíqua [3]

No Domain-Driven Design (DDD), a Linguagem Ubíqua (Ubiquitous Language) é o idioma único e rigorosamente compartilhado por especialistas de domínio (negócio) e engenheiros de software.

Cenário Sem Linguagem Ubíqua

O time comercial discute um "Contrato", o banco de dados armazena em uma tabela chamada "T_DOCUMENTO_LEGAL", e a API expõe uma rota /api/agreements. Essa dissonância gera bugs sistêmicos e lentidão na manutenção.

Cenário Com Linguagem Ubíqua

O termo é estritamente definido como Contrato. Ele existe no PRD, existe como uma classe Contrato no C#, é salvo na coleção Contratos e os eventos publicados na mensageria são ContratoAssinadoEvent.

01 – Domain-Driven Design

O Caso Prático da Prefeitura [3]

Considere uma administração pública onde diversos departamentos precisam lidar com o mesmo evento físico no mundo real, mas o nomeiam de forma fragmentada, gerando silos de informação:

Secretaria de Obras

"Avaria Asfáltica Tipo B"

Atendimento ao Cidadão

"Buraco na Rua"

Fiscalização de Trânsito

"Obstáculo em Via Pública"

Consequência Direta: A criação de múltiplos bancos de dados paralelos, relatórios administrativos duplicados, desperdício de dinheiro público e sistemas de software incapazes de trocar informações via API de forma coesa.

Bounded Context: a mesma palavra, modelos diferentes [4]

Um Bounded Context é a fronteira dentro da qual um modelo de domínio vale. Fora dela, o mesmo substantivo significa outra coisa. "Cliente" existe em toda a LogiTech, mas cada área precisa de um Cliente diferente.

Monolith First: por onde começar [4]

Martin Fowler observou um padrão: quase todo sistema de microsserviços bem-sucedido começou como um monólito que foi quebrado. E quase todo sistema que já nasceu em microsserviços acabou em apuros.

Takeaway

Errar a fronteira dentro de um monólito custa uma refatoração. Errar a fronteira entre microsserviços custa uma migração distribuída, com contrato de API, versionamento e dados espalhados.

SDLC: Ciclo de Vida de Desenvolvimento de Software [5]

O SDLC (Software Development Life Cycle) é a estrutura metodológica adotada por corporações para projetar, construir e manter softwares de alta qualidade.

1. Planejamento

Definição de requisitos corporativos (PRD), viabilidade financeira, estimativas e desenho de arquitetura (SDD).

2. Construção

Escrita de código limpo, aplicação de Design Patterns, versionamento rigoroso (Git) e revisões (Code Review).

3. Operação & Testes

Validação via Pirâmide de Testes, orquestração com Docker/Kubernetes, monitoramento contínuo e gestão de SLAs.

4. Descontinuação

O processo ordenado de desligar o software (Sunset), incluindo portabilidade de banco de dados e expiração de APIs antigas.

Evolução dos Sistemas de Controle de Versão [6]

A virada decisiva foi sair do modelo síncrono (servidor central, arquivo travado, precisa estar online) para o distribuído, em que cada máquina tem o repositório inteiro.

1972 – 1982 SCCS / RCS Local. Versiona arquivo a arquivo na própria máquina. Perdeu o disco, perdeu tudo.
1990 CVS Primeiro servidor central. Vários devs no mesmo projeto, mas merge frágil.
2000 SVN (Subversion) Centralizado e síncrono. Commit exige rede e o lock trava o arquivo para os demais.
2005 Git / Mercurial Distribuído e assíncrono. Clone integral do histórico, commit e branch offline.
2008 → hoje GitHub / GitLab O Git vira plataforma: Pull Request, CI/CD, code review e automação em cima do mesmo grafo.
Takeaway

Git venceu porque desacoplou o ato de versionar do ato de compartilhar. Você comita no avião; sincroniza quando quiser.

O Multiverso do Git

Em Guerra Infinita, o Doutor Estranho avança no tempo e observa 14.000.605 futuros possíveis. Ele explora cada linha isoladamente, descarta as que falham e volta ao presente sabendo qual seguir.

É literalmente o que o Git faz. A partir de um mesmo ponto da história você abre quantas realidades quiser, testa cada uma sem risco, joga fora as que não deram certo e traz de volta só a que funcionou.

A diferença é que no Git você não precisa da Joia do Tempo: git branch resolve, e sai de graça.

01 – Git Branching
21

O que é, de fato, um commit

Um commit não é "um pedaço de mudança": é uma fotografia completa e imutável do projeto inteiro, endereçada por um hash e ligada ao commit anterior.

Cada commit aponta para o anterior

Essa corrente é a história do projeto. Percorrê-la de trás para frente é o que permite git log, git blame e git revert.

Imutável por construção

O hash vem do conteúdo. Alterar um commit antigo muda o hash dele e o de todos os seguintes: a adulteração fica evidente.

O tamanho certo

Uma mudança coerente, que você reverteria sozinha. "Fim do dia" não é commit; "corrige o frete do PAC" é.

01 – Commits
22

O que é, de fato, uma branch

Aqui está a parte que quase todo mundo entende errado: uma branch não é uma cópia do projeto. É um arquivo de 41 bytes contendo o hash de um commit. Criar uma branch é instantâneo porque nada é copiado.

Na prática

Como a branch é só um ponteiro, "trocar de branch" é o Git reescrever seus arquivos para o estado daquele commit. Por isso ele reclama quando há trabalho não commitado: ele não tem onde guardar o que você ainda não salvou.

Estratégias Avançadas de Branching [6]

Trunk-Based Development

Modelo de alta frequência onde os desenvolvedores integram atualizações curtas e constantes (várias vezes ao dia) diretamente na ramificação principal. Requer disciplina excepcional, uso de Feature Flags e automação de testes exaustiva. Padrão nas principais Big Techs.

GitFlow Pattern

Estratégia mais burocrática, que cria ramificações de longa vida nominalmente isoladas (develop, release, hotfix). É apropriada e recomendada para softwares sob estritas regulações de compliance e ciclos de lançamento engessados de menor frequência.

O Modelo OSI (Open Systems Interconnection) [7]

O OSI é um modelo de referência didático de sete camadas. O que roda de fato na internet é a pilha TCP/IP, com quatro. Saber mapear uma na outra é o que permite localizar um problema.

Onde cada camada te encontra no dia a dia

L7 a API que você escreve (HTTP, gRPC).
L6 o TLS do cadeado do navegador.
L4 a escolha entre TCP e UDP: o tema da Aula 01.
L3 o IP e a rota até o destino.
L2/L1 o cabo, o Wi-Fi, o 5G.

Takeaway

A camada define onde você depura. Latência alta em uma query é L7; pacote que nunca chega é L3/L4; o site abre em HTTP e falha em HTTPS é L6. Diagnosticar sem saber a camada é chutar.

01 – Modelo de Referência OSI
27

Camada de Transporte (L4): Protocolo TCP [7]

Caso de uso: uma transferência bancária de R$ 2.500,00. Aqui, perder um pacote em silêncio é inaceitável, então o protocolo confirma cada etapa antes de prosseguir.

Quando usar

Integridade vale mais que milissegundos: transação financeira, escrita em banco, upload de arquivo, e-mail. Se um segmento não for confirmado, o TCP retransmite sozinho e reordena na chegada. O preço é o overhead do handshake.

01 – Protocolo TCP
28

Camada de Transporte (L4): Protocolo UDP [7]

Caso de uso: o rastreador GPS de um caminhão da LogiTech, emitindo posição a cada segundo. Sem handshake e sem confirmação: o datagrama sai e o emissor nunca sabe se chegou.

Quando usar

Frescor vale mais que completude: telemetria, GPS, voz e vídeo ao vivo, jogos, DNS. A posição de um segundo atrás não interessa mais, então retransmitir seria pior que perder. Nunca em transação financeira.

Passo 4 de 5: Revisar criticamente (a parte avaliada)

O modelo vai errar. Encontrar onde ele errou é a competência que a disciplina quer desenvolver. Passem os dois documentos por esta checklist:

Requisito que não dá para testar

"O sistema deve ser rápido" não é requisito. Qual latência, medida em qual percentil, sob qual carga?

Termo com dois nomes

O PRD diz "entrega" e o SDD diz "remessa"? A Linguagem Ubíqua já quebrou na primeira página.

Justificativa decorada

O SDD explicou o que é UDP, ou explicou por que este requisito pede UDP? Só o segundo conta.

Requisito que ninguém pediu

Modelos inventam funcionalidade para parecer completos. Apaguem o que não veio do problema.

Obrigatório

Acrescentem ao final do PRD uma seção "Revisão da Dupla" dizendo o que corrigiram e por quê. Sem ela, a entrega fica incompleta.
