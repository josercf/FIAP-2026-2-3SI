Bounded Contexts

Vocês separaram Telemetria de Pedidos, Faturamento e Atendimento. Hoje a API que sobe é a do contexto de Telemetria, e só dele.

Linguagem Ubíqua

O glossário do SDD vira nome de rota, de campo JSON e de evento SSE. Se lá está Posicao, a rota não pode devolver location.

TCP ou UDP, justificado por RNF

Regra do dia

02 – Resgate da Espiral

O Desafio do Mini Mundo: a torre de controle da LogiTech

Os 400 caminhões já emitem posição por socket UDP. O problema agora é de consumo: a sala de operações precisa ver isso em um painel no navegador, e o navegador não fala socket cru.

O QUE TEMOS DEPOIS DA AULA 01

Um processo Python escutando datagramas na porta 8081. Para ler os dados é preciso ter acesso ao servidor, abrir um terminal e olhar o log. Nenhum operador de logística vai fazer isso.

O QUE PRECISA EXISTIR HOJE

Um endereço que qualquer navegador abre, que devolve a posição da frota em JSON e que empurra cada nova posição para a tela sem o operador apertar F5.

Dor 1: ninguém sabe ler

Byte cru não tem verbo, não tem status e não tem tipo de conteúdo. Cada cliente inventaria o próprio formato.

Dor 2: atualização por F5

Um painel consultando a cada 5 segundos faz 17.280 requisições por dia, quase todas devolvendo o que já se sabia. Multiplique pelo número de operadores.

Dor 3: nada é inspecionável

Quando a posição atrasa, não há como dizer se o problema é rede, servidor ou painel. Falta um protocolo com semântica.

Do Socket L4 ao HTTP L7: o que subiu de camada [1]

O HTTP não substitui o TCP: ele roda em cima do mesmo socket que vocês abriram na Aula 01. O que ele acrescenta é o combinado de como conversar dentro daquele fluxo de bytes.

02 – L4 para L7
6

Anatomia de uma mensagem HTTP [1]

Até o HTTP/1.1 a mensagem é texto: linha inicial, headers, linha em branco e corpo. Saber isso de cor é o que permite depurar com curl qualquer integração que falhe.

REQUISIÇÃO
GET /api/v1/posicoes?placa=ABC1D23 HTTP/1.1
Host: telemetria.logitech.com
Accept: application/json
Authorization: Bearer eyJhbGciOi...
User-Agent: painel-operacao/1.4

Linha inicial: método + alvo + versão. Depois headers, uma linha em branco e o corpo (aqui vazio).

RESPOSTA
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 49
Cache-Control: max-age=5

{"placa":"ABC1D23","lat":-23.5505,"lng":-46.6333}

Linha inicial: versão + status + razão. O corpo só é interpretável por causa do Content-Type.

Takeaway

Toda a semântica do HTTP cabe em quatro elementos: método, alvo, status e headers. O corpo é opcional e, sozinho, não significa nada.

02 – Mensagem HTTP
7

Verbos HTTP: intenção, segurança e idempotência [1]

Seguro significa que não altera estado. Idempotente significa que repetir a chamada dá o mesmo resultado que fazer uma vez. É o que decide se o cliente pode reenviar quando a rede cai.

VerboSeguroIdempotenteNa API de telemetria da LogiTech
GETSimSimGET /api/v1/posicoes devolve a última posição de cada caminhão
POSTNãoNãoPOST /api/v1/ocorrencias registra uma parada não planejada; repetir cria duas
PUTNãoSimPUT /api/v1/caminhoes/ABC1D23 substitui o cadastro inteiro; repetir dá no mesmo
PATCHNãoDependePATCH /api/v1/caminhoes/ABC1D23 altera só o motorista designado
DELETENãoSimDELETE /api/v1/ocorrencias/77 apaga; repetir devolve 404, mas o estado final é o mesmo
Por que isso importa

O rastreador do caminhão perde sinal no meio do envio e não sabe se a chamada chegou. Se o verbo for idempotente, ele reenvia sem medo. Se for POST, reenviar duplica a ocorrência no painel do operador.

02 – Verbos HTTP
8

Status Codes: de quem é a culpa [1]

A primeira classe já separa responsabilidade: 4xx é erro de quem chamou, 5xx é erro de quem respondeu. Devolver 200 com {"erro": ...} no corpo destrói essa informação.

02 – Status Codes
9

Headers: onde mora a engenharia [1]

Header não é enfeite: é o contrato de formato, cache, identidade e conexão. A maior parte dos incidentes de integração que vocês vão ver na carreira é briga de header.

HeaderPara que serveEfeito prático na LogiTech
Content-TypeDeclara o formato do corpoSem application/json, o painel recebe texto e o parse quebra
AcceptDiz o que o cliente sabe lerO mesmo endpoint pode servir JSON ao painel e CSV ao BI
AuthorizationCarrega a credencialToken do operador; sem ele a resposta é 401, não 200 vazio
Cache-ControlDefine quem pode guardar e por quanto tempomax-age=5 na consulta de posição; no-cache obrigatório no stream SSE
Connection / Keep-AliveMantém a conexão TCP abertaEvita repetir o handshake a cada requisição do painel
ETag / If-None-MatchIdentifica a versão do recursoPermite responder 304 quando a posição não mudou desde a última consulta
Takeaway

Headers custam bytes em toda requisição. No HTTP/1.1 eles vão em texto, sem compressão. Guardem isso: é exatamente o que o HTTP/2 ataca com o HPACK.

02 – Headers HTTP
10

HTTP/1.1: uma fila só, e o Head-of-Line blocking [2]

No HTTP/1.1 cada conexão TCP atende uma requisição por vez. Se a primeira demora, as demais esperam, mesmo que já estivessem prontas no servidor. Isso é o Head-of-Line blocking.

02 – HTTP/1.1
11

HTTP/2: frames binários e multiplexação [2]

O HTTP/2 troca o texto por frames binários, cada um marcado com o número do seu stream. Frames de streams diferentes viajam intercalados na mesma conexão TCP e são remontados na chegada.

02 – HTTP/2
12

HTTP/3: o bloqueio que sobrou era do TCP [2]

O HTTP/2 resolveu o bloqueio na camada HTTP, mas o TCP continua entregando um fluxo único e ordenado: um pacote perdido trava tudo o que vem depois, inclusive frames de outros streams. O HTTP/3 troca o TCP pelo QUIC, que roda sobre UDP.

02 – HTTP/3 e QUIC
13

Quadro comparativo: 1.1, 2 e 3 [2]

AspectoHTTP/1.1 (1997)HTTP/2 (2015)HTTP/3 (2022)
TransporteTCPTCPQUIC sobre UDP
FormatoTextoFrames bináriosFrames binários
ConcorrênciaUma mensagem por conexão; navegador abre até 6Streams multiplexados em uma conexãoStreams independentes de verdade
Head-of-LineNa camada HTTP e na de transporteResolvido no HTTP, permanece no TCPResolvido nas duas

CriptografiaOpcional (TLS por cima)Opcional na norma, obrigatória na prática dos navegadoresIntegrada ao protocolo (TLS 1.3)

Para a LogiTech

O painel da torre de controle abre dezenas de recursos ao mesmo tempo: HTTP/2 já paga a conta. O aplicativo do motorista, em 4G instável trocando de antena, é o caso em que o HTTP/3 faz diferença mensurável.

02 – Comparativo HTTP
14

O handshake TLS: como nasce o cadeado [3]

O HTTPS é o mesmo HTTP dentro de um túnel TLS. Antes de qualquer byte de aplicação, cliente e servidor negociam a versão, provam identidade por certificado e derivam a chave de sessão.

Por que isso pesa

Esse RTT se soma ao do handshake TCP em toda conexão nova. Em uma rede móvel de 100 ms, são 200 ms gastos antes de a primeira posição de caminhão sair do servidor. É exatamente esse custo que o QUIC funde em um só.

02 – Handshake TLS
15

Server-Sent Events: uma resposta que não termina [4]

SSE não é protocolo novo: é uma resposta HTTP 200 OK com Content-Type: text/event-stream que o servidor mantém aberta e vai alimentando. O corpo é texto, linha a linha.

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

retry: 3000
id: 1
event: posicao
data: {"placa":"ABC1D23","lat":-23.55}

id: 2
event: posicao
data: {"placa":"ABC1D23","lat":-23.56}

data: e a linha em branco

Cada evento termina em linha vazia. Esquecer o \n\n é o bug número um: o painel parece travado.

id: e retry:

Caiu a conexão, o navegador reconecta depois de retry ms e manda Last-Event-ID, continuando de onde parou.

No cliente

new EventSource('/api/v1/eventos') e um listener. Sem biblioteca, sem dependência.

Cuidado de produção

Proxies costumam bufferizar respostas. Sem no-cache e sem desligar o buffer no proxy, os eventos chegam em lote e o painel mostra a frota no passado.

02 – Server-Sent Events
16

SSE contra WebSocket: por que aqui basta o mais simples [5]

Como escolher

Pergunte quem fala. Só o servidor fala: SSE. Os dois falam, com latência apertada: WebSocket. Escolher WebSocket para tráfego de sentido único é pagar reconexão manual e protocolo próprio por uma capacidade que não vai ser usada.

02 – SSE e WebSocket
17

cURL: enxergar o protocolo sem sair do terminal [6]

O navegador esconde o protocolo: mostra a página pronta e engole os detalhes. O curl devolve a mensagem exatamente como ela vai e volta, e é a primeira ferramenta a abrir quando uma integração falha.

# -i mostra os headers da resposta junto com o corpo
curl -i http://localhost:3000/api/v1/posicoes

# -v mostra a conversa inteira: conexao, requisicao enviada e resposta recebida
curl -v http://localhost:3000/health

# -N desliga o buffer: obrigatorio para acompanhar um stream SSE ao vivo
curl -N http://localhost:3000/api/v1/eventos

# -X forca o verbo: prova que a rota devolve 405 quando o metodo e errado
curl -i -X POST http://localhost:3000/api/v1/posicoes

# -w imprime metricas medidas pelo proprio curl, sem cronometro na mao
curl -o /dev/null -s -w "conexao: %{time_connect}s total: %{time_total}s\n" \
  http://localhost:3000/api/v1/posicoes
No laboratório

Estes cinco comandos são o roteiro inteiro do Passo 4.

02 – Inspeção com cURL

Lendo a saída do curl -v, linha a linha [6]

Cada prefixo tem significado: * é o que o curl fez na rede, > é o que ele enviou e < é o que recebeu. É a aula inteira em uma tela.

Primeiro diagnóstico

Antes de acusar o código, rode o curl -v. Ele responde em segundos se a falha é de conexão, de requisição malformada ou de resposta errada, e isso já elimina duas das três hipóteses.

Git Workflow: da branch ao merge, passando pela revisão [7]

Na Aula 01 vocês comitaram direto na main, porque estavam sozinhos no repositório e entregavam documento. Hoje entra código, e código quebra: por isso o trabalho vai para uma branch e só chega à main depois de revisado.

Nome de branch

02 – Git Workflow

Code Review: o que se olha em um Pull Request [7]

Revisar não é procurar erro de digitação. É responder uma pergunta: eu assumiria a manutenção deste código?

1. Faz o que a descrição diz

O PR promete o stream de posições e altera o cálculo de frete? São dois PRs, não um.

2. Respeita a Linguagem Ubíqua

O SDD diz Posicao e o JSON devolve location. Comentário obrigatório: o domínio vazou.

3. Trata o caminho infeliz

O que acontece se o coletor estiver fora? Devolve 503 ou trava a conexão sem resposta?

4. É verificável

Existe comando que prove que funciona? Se o revisor não consegue rodar, não consegue aprovar.

Como comentar

Comentário útil aponta a linha, diz o efeito e propõe o caminho: "na linha 42, sem a linha em branco depois do data: o navegador não dispara o evento; sugiro terminar a escrita com \n\n". Comentário inútil diz "melhorar isso aqui".

  • A Abrindo uma conexão TCP nova para cada arquivo pedido pela página.
  • B Dividindo as mensagens em frames binários identificados por stream, que viajam intercalados na mesma conexão TCP.

Passo 4 de 5: Medir o próprio serviço com cURL

Não é relatório: são três perguntas com resposta numérica, registradas em docs/OBSERVACOES.md. Dez minutos, só com o que o devcontainer já tem.

Passo 5 de 5: Pull Request e Code Review cruzado

A entrega é o Pull Request aprovado, não o código solto. Quem aprova é a dupla vizinha, adicionada como colaboradora.

git add http-l7/ docs/OBSERVACOES.md
git commit -m "feat(api): expoe posicoes da frota via HTTP"
git commit -m "feat(sse): transmite posicoes novas por SSE"
git push -u origin feature/http-telemetry

# abrir o PR: feature/http-telemetry -> main

O que o PR precisa ter

No mínimo 2 commits em Conventional Commits e uma descrição com 3 seções: o que mudou, como testar e o que ficou de fora.

O que a revisão precisa ter

No mínimo 2 comentários em linha, cada um apontando linha, efeito e sugestão, e 1 aprovação registrada em Review.

Ordem que vale

Merge só depois da aprovação. Se aprovarem sem ler, a dupla revisora responde pelo que passou: é assim no mercado e é assim aqui.
