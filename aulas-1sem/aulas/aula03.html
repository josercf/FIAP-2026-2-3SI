03 – Resgate da Espiral

Desafio do Mini Mundo: "na minha máquina funciona"

O coletor da LogiTech roda perfeito no notebook de quem o escreveu. No servidor de homologação, o Python é outro, falta dependência, o caminho do arquivo de dados não existe. Cada ambiente é uma máquina montada à mão, e nenhuma é igual à outra.

O sintoma

Deploy que funciona às 15h e quebra às 15h40, porque a máquina de produção tinha outra versão de runtime.

A causa

O artefato entregue era só o código. O ambiente (runtime, dependências, variáveis, caminhos) ficava por conta de cada máquina.

A missão de hoje

Entregar o ambiente junto com o código: uma imagem que roda idêntica no seu notebook, no Codespace e no servidor.

Restrição de gente grande

Não basta funcionar: a imagem de produção precisa ser mínima. Imagem de 1,6 GB para um script é custo de rede, de disco e de superfície de ataque, e hoje vocês vão medir essa diferença.

03 – Isolamento de Processos
8

chroot: o primeiro isolamento, e por que não basta [1]

Desde 1979 o Unix sabe trocar a raiz do sistema de arquivos de um processo: depois de chroot /jaula, o processo enxerga /jaula como se fosse /. Parece um container, mas só resolve um dos recursos compartilhados.

O que o chroot isola

A visão do sistema de arquivos: o processo não alcança nada fora da nova raiz (com as ferramentas certas, até isso escapa).

O que continua compartilhado

A árvore de PIDs, a pilha de rede e as portas, o hostname, a memória e a CPU sem limite algum. O processo enjaulado ainda derruba o host inteiro.

A pergunta que o kernel respondeu

E se cada recurso do sistema (processos, rede, montagens, hostname) pudesse ter a sua própria "troca de raiz"? Essa generalização são os namespaces, o próximo slide.

03 – Isolamento de Processos
10

cgroups: namespaces escondem, cgroups limitam [1]

Namespace controla o que o processo enxerga; cgroup controla o que ele consome. Sem cgroup, um coletor com vazamento de memória continua derrubando o host inteiro, por mais isolado que esteja.

03 – Isolamento de Processos
11

Container = processo + namespaces + cgroups + rootfs [1]

Processo

Um processo Linux comum, visível no ps do host. Não existe "máquina" nenhuma.

+ Namespaces

As seis paredes: ele só enxerga o próprio mundo de PIDs, rede, montagens, hostname, IPC e usuários.

+ cgroups

Teto de memória, CPU e I/O. O vizinho barulhento não derruba mais o host.

+ rootfs

Um sistema de arquivos próprio, empacotado na imagem: runtime, dependências e código juntos.

Definição para levar para a prova: container é um processo Linux comum, isolado por namespaces, limitado por cgroups e enxergando um sistema de arquivos que veio de uma imagem. Nada mais que isso.

Consequência direta

Container sobe em milissegundos e não desperdiça memória com kernel próprio, porque é só um processo. Essa é a diferença estrutural para a máquina virtual do próximo slide.

03 – Isolamento de Processos
12

Container x máquina virtual [2]

Quando cada um

VM isola com kernel próprio: fronteira mais dura, custo maior. Container compartilha o kernel do host: denso e rápido, ideal para empacotar serviços como os da LogiTech. Não são rivais: o seu Codespace é uma VM rodando containers.

03 – Atividade 1
15

Imagem x container: o molde e a instância [2]

Imagem

Imutável e compartilhável. O rootfs empacotado em camadas: runtime, dependências, código e metadados (qual comando rodar, quais portas expor). É o que se versiona, se publica e se audita.

Container

Vivo e descartável. Um processo criado a partir da imagem, com uma camada gravável em cima. Da mesma imagem saem dez containers idênticos, e destruir um não afeta os outros.

Analogia direta com a Aula 05 que vem aí: a imagem está para o container como a classe está para o objeto. Ninguém edita um objeto para mudar a classe; ninguém edita um container para mudar a imagem.

Regra operacional

Mudou o código? Constrói-se uma imagem nova e sobe-se um container novo. Entrar num container em produção para "dar um jeitinho" destrói a reprodutibilidade que justificou o Docker.

Camadas e union filesystem [2]

03 – Imagem e Camadas
17

A camada gravável morre junto com o container [2]

Tudo que o processo escreve (logs, uploads, o telemetria.jsonl do coletor) vai para a camada gravável. E a camada gravável pertence ao container, não à imagem.

docker stop

O processo para, a camada gravável continua existindo. Um docker start devolve tudo como estava.

docker rm

O container é destruído e a camada gravável vai junto, sem lixeira. O que não estava em volume deixou de existir.

Por desenho, não por defeito

Efemeridade é o que permite tratar container como gado, não como bicho de estimação: destruir e recriar é a operação normal.

A pergunta que fica armada

Se a telemetria da LogiTech é receita rastreada e a camada gravável evapora no primeiro rm, onde esses dados deveriam morar? Segurem essa pergunta: ela é o Ciclo 5, depois do intervalo.

03 – Dockerfile e Build
23

CMD x ENTRYPOINT [3]

CMD: o padrão substituível

O que roda se ninguém pedir outra coisa. Qualquer argumento no docker run o substitui inteiro.

CMD ["python", "server_telemetry.py"]
# docker run img            -> roda o coletor
# docker run img sh         -> abre o shell, CMD ignorado

ENTRYPOINT: o executável fixo

Sempre roda; os argumentos do docker run viram parâmetros dele. CMD, se existir, vira o parâmetro padrão.

ENTRYPOINT ["python", "server_telemetry.py"]
CMD ["--porta", "8081"]
# docker run img --porta 9090 -> troca só o parâmetro
Regra prática

Serviço com um executável claro, como o coletor: ENTRYPOINT para o programa, CMD para os parâmetros padrão. Imagem de propósito geral, como a alpine: só CMD. Sempre na forma de lista JSON, que não abre shell intermediário.

.dockerignore e o contexto de build [3]

O . no fim do docker build -t img . é o contexto: tudo daquele diretório é enviado ao daemon antes do build começar. Sem filtro, vão junto o .git, o node_modules, os dados de teste e qualquer segredo esquecido.

.dockerignore do lab de hoje

.git
node_modules
__pycache__

etapas/
docs/

Build mais rápido

Contexto pequeno viaja em milissegundos. Um node_modules de 300 MB no contexto atrasa todo build.

Cache mais estável

Arquivo irrelevante que muda (um log, um dado de teste) invalida o cache do COPY sem necessidade.

Segredo fora da imagem

O que não entra no contexto não tem como vazar para dentro de uma camada.

A base importa: full, slim, alpine, distroless [4]

BaseOrdem de grandezaO que trazQuando usar
python:3.12~1 GBDebian inteiro, compiladores, headersBuild de dependência nativa complicada
python:3.12-slim~150 MBDebian enxuto, sem toolchainCompatibilidade glibc com tamanho razoável

Alpine usa musl em vez de glibc: pacote Python com binário nativo pode precisar compilar. Para o coletor, que é biblioteca padrão pura, é indiferente; num projeto com NumPy a conta muda, e a slim pode sair mais barata que a alpine compilando.

Decisão de engenharia, não de moda

A escolha da base é um trade-off entre tamanho, compatibilidade e capacidade de depuração. O que não se defende em revisão de código é a full em produção sem justificativa.

03 – Multi-Stage
32

Usuário não-root, e o que nunca entra na imagem [4]

Por padrão, o processo roda como root

FROM python:3.12-alpine AS runtime
RUN adduser -D -u 10001 logitech
WORKDIR /app
COPY --from=builder /build/server_telemetry.py .
USER logitech
EXPOSE 8081/udp
CMD ["python", "server_telemetry.py"]

Escapou uma falha no processo? Como root do container, o estrago possível é muito maior. USER custa duas linhas.

Nunca entra na imagem final

Compilador, gerenciador de pacotes, testes, .git, node_modules de desenvolvimento e o próprio Dockerfile.

Segredo, jamais

ENV e camada são permanentes: um docker history revela tudo. Segredo entra em execução, por variável ou secret manager.

Onde os dados da LogiTech estão morrendo [5]

O coletor conteinerizado grava cada posição de caminhão em /dados/telemetria.jsonl. Esse caminho, hoje, mora na camada gravável. A frota reporta a noite inteira e, no primeiro docker rm (um deploy, um crash, um nó que recicla), o histórico completo evapora.

Não é bug do Docker

É o comportamento de projeto que a Atividade 2 provou e o Quiz 1 revisou antes do intervalo. Efemeridade é o padrão.

É decisão de arquitetura

Estado precisa ser declarado e movido para fora do container: o serviço continua descartável, o dado não.

O contrato já existe

O caminho vem da variável LOGITECH_DADOS, declarada no Dockerfile. Falta apontar esse caminho para um lugar que sobreviva.

O que resolve

Montar um volume no /dados: o container escreve no mesmo caminho de sempre, mas os bytes passam a viver no host, administrados pelo Docker, indiferentes ao rm.

03 – Volumes
37

Os comandos de volume [5]

docker volume create logitech-telemetria          # cria (ou o -v cria sozinho no 1º uso)
docker volume ls                                  # lista os volumes do host
docker volume inspect logitech-telemetria         # onde os bytes moram, quem usa

docker run -d --name coletor \
  -v logitech-telemetria:/dados \
  coletor:final                                   # monta o volume no /dados do container

docker volume rm logitech-telemetria              # remove (recusa se um container usa)
docker volume prune                               # remove os órfãos, com confirmação

O rm do container nunca remove o volume: são ciclos de vida separados, e é exatamente esse o objetivo. Volume só morre por docker volume rm explícito.

Leitura do inspect

O Mountpoint mostra o diretório real no host onde o Docker guarda os bytes. O container não sabe e não precisa saber: ele só enxerga o /dados de sempre.

Publicar porta, observar e limitar [6]

docker run -d --name gateway --network logitech-net \
  -p 3000:3000 gateway:final        # host:container; só o que tem -p sai da rede

docker stats --no-stream           # CPU, memória e I/O de cada container, ao vivo
docker inspect coletor             # o JSON completo: IP na rede, mounts, limites

docker run -d --memory 256m --cpus 0.5 coletor:final   # o teto vira cgroup

-p publica, EXPOSE documenta

Sem -p, o serviço só existe dentro da rede. O gateway precisa de -p 3000:3000; o coletor, acessado só pelo gateway, não precisa expor nada ao host.

stats fecha o ciclo

O mesmo cgroup do Ciclo 1, agora visto de cima: o docker stats mostra o consumo real contra o limite declarado.

Limite é contrato

--memory e --cpus transformam capacidade em número auditável, por serviço, antes de existir orquestrador.

IA que constrói container: o que é uma Agent Skill [8]

Pedir no chat, toda vez

"Escreva um Dockerfile multi-stage, base alpine, usuário não-root, sem COPY . . ..." O conhecimento mora na sua memória e se perde a cada conversa. Cada colega pede de um jeito, sai um padrão diferente por dia.

Skill: o padrão versionado

As regras moram num arquivo SKILL.md dentro do repositório. O agente carrega a skill sob demanda, quando a descrição dela casa com a tarefa, e o padrão passa pelo mesmo Git, revisão e evolução que o código.

Sob demanda é o ponto central: a skill não é colada no prompt. O agente enxerga só o nome e a descrição de cada skill disponível; o corpo com as regras só é lido quando a tarefa pede. Dez skills no repositório não custam contexto até serem necessárias.

Por que isso importa para a LogiTech

O padrão de Dockerfile que vocês consolidaram hoje vira ativo da empresa: um arquivo que qualquer agente de IA do time lê, aplica e mantém consistente, em vez de tradição oral de prompt.

Anatomia do SKILL.md [8]

name: logitech-dockerfile

  servicos da plataforma LogiTech, em Python e Node

# Dockerfile da LogiTech

## Regras que não se negociam

1. Sempre dois estágios nomeados, builder e runtime.
2. Base alpine no estágio final. Nunca base full.
3. Usuário não-root, com UID acima de 10000.
4. Nunca COPY . . : nomear cada arquivo que entra.
5. EXPOSE com a porta real: 8081/udp ou 3000.
6. Caminho de dados vem de LOGITECH_DADOS.

Frontmatter: a vitrine

name e description são o que o agente enxerga o tempo todo. É pela descrição que ele decide acionar a skill.

Corpo: as regras

Lido só quando a skill é acionada. Imperativo, curto e verificável: são as mesmas regras do slide de não-root, palavra por palavra.

Este arquivo existe no lab

É a .agents/skills/logitech-dockerfile/SKILL.md do repositório que vocês forkaram, a mesma da demonstração a seguir.
