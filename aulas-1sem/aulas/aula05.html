Desafio do Mini Mundo: cobrar sem prender a regra

A LogiTech vai faturar os fretes que já sabe fazer. E a área comercial fecha contrato diferente com cada cliente: boleto para o cliente comum, cartão corporativo com desconto para o cliente ouro, e agora fatura mensal para quem assina contrato.

O que o negócio pede

Um contrato comercial novo entra em produção em dias, não em meses. Ninguém aceita ouvir que mudar a forma de cobrança exige reescrever o serviço de pedidos.

O que o código costuma virar

Um if a mais por contrato, dentro do mesmo método, num arquivo que também sabe salvar no banco e montar a resposta HTTP. Em seis meses ninguém encosta nele.

A pergunta de projeto da noite: onde essa decisão deveria morar para que o serviço de Pedidos não precise mudar quando o comercial fechar o próximo contrato?

O alvo

Gravar pedido e emitir fatura sem que a regra de negócio conheça o banco de dados nem o meio de pagamento de cada cliente.

A correção: métodos de negócio

public class Pedido {
    private StatusPedido status;
    private BigDecimal valor;

    public void faturar(String nf) {
        exigirTexto(nf, "numeroNotaFiscal");
        this.numeroNotaFiscal = nf;
        this.status = StatusPedido.FATURADO;
    }

    public void alterarEndereco(String novo) {
        exigirTexto(novo, "novoEndereco");
        if (status == StatusPedido.ENTREGUE)
            throw new IllegalStateException(
                "pedido já entregue");
        this.enderecoEntrega = novo;
    }
}
Takeaway

Setter público para todo campo não encapsula nada. A regra "pedido entregue não muda de endereço" precisa morar no objeto: na Aula 08 quem vai pedir essa alteração é um agente de IA, e a regra tem que valer para ele também.

O cheiro

@Service
public class PedidoService {

  public Pedido criar(NovoPedido novo) {
    // 1. regra de negócio
    Pedido p = new Pedido(...);
    // 2. montagem de JSON na mão
    String corpo = "{\"pedidoId\":\"" + p.getId()
        + "\",\"valor\":" + p.getValor() + "}";
    // 3. detalhe de rede
    HttpRequest r = HttpRequest.newBuilder()
        .uri(URI.create("http://localhost:5080"
             + "/api/v1/faturas"))
        .POST(ofString(corpo)).build();
    // 4. persistência
    entityManager.persist(p);
    return p;
  }
}

A correção

@Service
public class PedidoService {

  private final PedidoRepository repositorio;
  private final ClienteFaturamento faturamento;
  private final ConectorFaturamentoFactory conectores;

  public Pedido criar(NovoPedido novo) {
    Pedido pedido = new Pedido(...);
    SolicitacaoFatura solicitacao =
        conectores.para(novo.tipoCliente())
                  .montar(pedido);
    try {
      pedido.faturar(faturamento.emitir(solicitacao));
    } catch (FaturamentoIndisponivelException e) {
      pedido.aguardarFaturamento();
    }
    return repositorio.salvar(pedido);
  }
}
// JSON, timeout e SQL moram na infraestrutura
Como reconhecer

Se você consegue contar, dentro de um método, quantas áreas diferentes da empresa poderiam pedir uma alteração nele, cada uma delas é uma responsabilidade que deveria estar em outro lugar.

L · Substituição de Liskov: o subtipo que quebra a promessa [2]

Como reconhecer

Substituibilidade não é conferida pelo compilador: ela vive nas promessas que o tipo não escreve. Se o subtipo entrega menos do que a interface promete, quem chama vai quebrar, e vai quebrar em produção.

/**
 * Contrato explícito, não subentendido:
 * montar() devolve sempre uma solicitação

public interface ConectorFaturamento { ... }

05 – Factory Method
25

Factory Method: o código que vocês vão escrever no TODO-2

@Component
public class ConectorFaturamentoFactory {

    private final Map<String, ConectorFaturamento> porTipoDeCliente;

    // O Spring injeta AQUI todos os beans que implementam ConectorFaturamento.
    // Nenhum registro à mão, nenhuma lista para manter em outro arquivo.
    public ConectorFaturamentoFactory(List<ConectorFaturamento> conectores) {
        this.porTipoDeCliente = conectores.stream().collect(
                Collectors.toMap(ConectorFaturamento::tipoClienteAtendido, Function.identity()));
    }

    public ConectorFaturamento para(String tipoCliente) {
        ConectorFaturamento conector = porTipoDeCliente.get(tipoCliente);
        if (conector == null) {
            throw new ConectorNaoEncontradoException(tipoCliente);
        }
        return conector;
    }
}

Repare no que a fábrica não tem: nenhum if, nenhum nome de tipo de cliente escrito no código dela. Quem sabe qual tipo atende é cada conector, no seu próprio arquivo.

Takeaway

Factory Method resolve uma pergunta só: quem tem o direito de decidir qual implementação usar. Tirar essa decisão da regra de negócio é o que a torna fechada para modificação.

A corrida acontece entre ler e gravar [6]

Por que o teste de vocês vai falhar

Ler, somar e gravar são três passos, e nada impede outra thread de entrar no meio. No laboratório vocês vão disparar 100 emissões concorrentes e ver o número de notas repetidas com os próprios olhos, antes de corrigir.

05 – Singleton e Concorrência

Singleton: o cheiro e as duas correções em C# [6]

O que o esqueleto entrega

public sealed class NumeradorNotaFiscal
{
    private static NumeradorNotaFiscal? _instancia;
    private int _ultimo;

    // criação sem sincronização: duas threads
    // na primeira chamada criam dois numeradores
    public static NumeradorNotaFiscal Instancia
        => _instancia ??= new NumeradorNotaFiscal();

    public string Proximo()
    {
        int atual = _ultimo;   // lê
        atual = atual + 1;     // soma
        _ultimo = atual;       // grava
        return $"NF-{atual:D6}";
    }
}

O que vocês entregam no TODO-5

public sealed class NumeradorNotaFiscal
{
    private static readonly Lazy<NumeradorNotaFiscal>
        _instancia = new(() => new NumeradorNotaFiscal(),
            LazyThreadSafetyMode.ExecutionAndPublication);

    private readonly object _trava = new();
    private int _ultimo;

    public static NumeradorNotaFiscal Instancia
        => _instancia.Value;

    public string Proximo()
    {
        lock (_trava) { _ultimo = _ultimo + 1;
                        return $"NF-{_ultimo:D6}"; }
    }
    // alternativa sem lock:
    // Interlocked.Increment(ref _ultimo)
}
São dois defeitos, não um

A criação da instância e o incremento do contador são corridas diferentes, e cada uma pede a sua correção. Consertar só uma delas deixa o teste do TODO-6 falhando de vez em quando, que é o pior dos mundos.

Quiz de Verificação

Qual o risco de utilizar o padrão Singleton incorretamente em ambientes multithreaded?
  • A Nenhum: por existir uma instância só, o Singleton é naturalmente seguro entre threads.
  • B O risco é de consumo de memória, porque a instância nunca é liberada pelo coletor de lixo.
  • C Se a instância guarda estado mutável sem sincronização, duas threads podem ler o mesmo valor e produzir resultados repetidos ou perdidos, e a própria trava vira gargalo se for larga demais.
  • D O risco é de compilação: o compilador recusa campo estático mutável acessado por mais de uma thread.

Na preparação desta aula, três execuções seguidas deram 35, 41 e 44 notas duplicadas num Mac de 10 núcleos, e 19 num contêiner Linux limitado a 2 núcleos. O número de vocês vai ser outro: é isso que a corrida tem de característico.

Quatro armadilhas que custam tempo hoje

Corrigir o Singleton antes de escrever o teste

Aí não sobra corrida para observar, e NOTAS_DUPLICADAS_ANTES fica sem valor real. O commit do TODO-6 vem antes do commit do TODO-5, e o histórico do fork mostra isso.

Esquecer o @Component no conector novo

Sem a anotação, o Spring não coloca o conector na lista que a fábrica recebe, e o tipo CONTRATO responde com erro de conector não encontrado. O teste de unidade passa, porque nele vocês montam a lista à mão.

Criar a interface no pacote errado

PedidoRepository mora em dominio, não em infra. Quem declara o contrato é quem precisa dele: com a interface em infra, o serviço continua importando infraestrutura e o critério CA-01 reprova.

Pedido com status AGUARDANDO_FATURAMENTO

Significa que o serviço de Faturamento não foi alcançado. Confiram LOGITECH_FATURAMENTO_URL e se o serviço em C# está de pé. O pedido não é perdido de propósito: a queda de um contexto não pode derrubar o outro.
