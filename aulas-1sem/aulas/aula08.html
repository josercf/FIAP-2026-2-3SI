Desafio do Mini Mundo: duas perguntas, o dia inteiro

O atendimento da LogiTech responde à mão, o dia inteiro, às duas perguntas abaixo. As duas já existem como rota na API de Pedidos. O agente pode resolver as duas sozinho, desde que não ganhe acesso solto ao sistema.

"Onde está o meu pedido?"

Leitura pura. Se o agente errar o identificador, devolve o pedido errado, e o cliente percebe na hora. Custo do erro: baixo, reversível.

"Muda o endereço de entrega."

Escrita. Se o agente errar, um caminhão de 12 toneladas vai para o lugar errado, com o frete já pago. Custo do erro: alto, e nem sempre reversível.

A pergunta de engenharia da noite não é "o modelo consegue?". É: o que impede o modelo de fazer a coisa errada, e o que sobra registrado quando ele tenta.

08 – Function Calling
7

O que o modelo enxerga: a declaração da ferramenta [1]

O modelo nunca vê o seu código: vê este JSON, e é só dele que tira qual função chamar e com quais argumentos. O exemplo é a ferramenta de localizar caminhão, que não é tarefa do laboratório.

{
  "type": "function",
  "function": {
    "name": "localizar_caminhao",
    "description": "Devolve a última posição conhecida de um caminhão da frota da LogiTech.",
    "parameters": {
      "type": "object",
      "properties": {
        "placa": { "type": "string",
                    "description": "Placa do caminhão, no padrão Mercosul, como BRA2E19",
                    "pattern": "^[A-Z]{3}[0-9][A-Z0-9][0-9]{2}$" }
      },
      "required": ["placa"],
      "additionalProperties": false
    }
  }
}
Três campos, três papéis

name volta na resposta. description ensina o modelo a escolher. parameters é o JSON Schema que o seu código usa para validar. Os três são código, não comentário.

08 – Integração x Engenharia

JSON Schema: contrato executável, não documentação [2]

O mesmo objeto tem dois leitores, e é isso que o torna um contrato: o modelo o lê para saber o que preencher, e o seu código o lê para decidir se aceita o que veio preenchido.

Leitor 1: o modelo

Serializado no prompt. Nomes de campo, tipos, formatos e descrições guiam a escolha. Schema vago produz argumento vago.

Leitor 2: o seu validador

O mesmo dicionário, agora como regra executável. No laboratório, agente/validacao.py percorre required, type e pattern e devolve a lista de erros.

O anti-padrão mais comum: declarar um schema rico para o modelo e validar com um if frouxo no código. Declarar bonito e validar frouxo não protege ninguém. O que protege é o mesmo objeto servir aos dois leitores.

08 – O Schema Barrando
15

A descrição é interface, não comentário

Ensaio feito na construção deste laboratório, com o qwen3.5:2b local, a mesma família de modelo que roda no Codespace de vocês. Duas versões da mesma ferramenta, mudando só o texto da descrição:

Versão da descriçãoPergunta feitaO que o modelo fez
Completa, avisando que o CEP é obrigatório"Onde está o pedido PED-1042?"Chamou a ferramenta certa, com o argumento certo, em 3 de 3 execuções
CompletaMudar endereço sem informar o CEPNão chamou a ferramenta: pediu o CEP ao cliente, em 3 de 3 execuções
Enfraquecida: "Altera o endereço de entrega de um pedido."A mesma, sem CEPNão produziu chamada nenhuma: gastou o orçamento de tokens raciocinando e devolveu resposta vazia em 3 de 3 execuções

Condições da terceira linha, para o número ser reproduzível: temperature 0.1, num_predict 400 e num_ctx 8192. Sem limite de tokens, duas execuções da mesma pergunta não retornaram em 600 e em 900 segundos, e foram descartadas como inconclusivas.

A leitura honesta desses números

Descrição boa melhora muito o comportamento, e ainda assim não é garantia: com a descrição enfraquecida o modelo não ficou perigoso, ficou inútil. Prompt é otimização; schema é garantia. Só uma das duas você consegue provar em teste.

08 – Onde Validar
17

Command Pattern: a intenção vira objeto [3]

O padrão comportamental do GoF que encapsula uma requisição como objeto. Quando a requisição vira objeto, ela pode ser guardada, inspecionada, enfileirada, autorizada, registrada e desfeita. Uma chamada de função direta não pode nada disso.

O que o padrão dá a um agente

Autorização num ponto único, auditoria automática de tudo o que passa, desfazimento quando o comando sabe voltar atrás, e teste sem modelo nenhum na jogada.

O sinal de que falta o padrão

Quando alguém pergunta "quem mandou alterar aquele endereço às 3h da manhã?" e a resposta é procurar no log do servidor web, que não sabe que havia uma IA no meio.

A frase que resume a aula

Function Calling é o como o modelo pede. Command Pattern é o como o sistema decide. Sem o segundo, o primeiro é só uma chamada de API com um intermediário probabilístico no meio.

O Despachante: quatro etapas que nunca trocam de ordem [3]

A ordem é a garantia

Validar depois de executar é auditoria de estrago. Auditar só o sucesso é trilha que mente por omissão. É por isso que a ordem das quatro etapas não é negociável.

08 – O Despachante
20

Recusa é resultado, não exceção

A recusa volta para a conversa como resultado da ferramenta. É isso que permite o agente se recuperar sozinho, em vez de travar ou mentir para o cliente.

if erros:
    motivo = "; ".join(erros)
    self._auditar(nome, auditoria.RECUSADO, argumentos, motivo)   # registra a tentativa
    return Resultado(auditoria.RECUSADO, {
        "erro": "argumentos recusados pela validação",
        "detalhes": erros,
        "orientacao": "peça ao cliente os dados que faltaram e chame de novo",
    }, motivo)                                                     # devolve ao modelo

O que nunca fazer na recusa

Executar mesmo assim; completar o campo faltante com um padrão inventado; devolver sucesso silencioso; ou levantar exceção que derruba a conversa inteira.

O que acontece no laboratório

Recusada a tentativa sem CEP, o agente pede o CEP e chama de novo, agora completo. Uma linha RECUSADO e uma AUTORIZADO, as duas na trilha.

08 – Trilha de Auditoria
22

Três vereditos, três causas diferentes

VereditoQuem decidiuExecutou?O que investigar quando aparece demais
AUTORIZADOO schema aceitouSimNada, mas confira se a ferramenta certa está sendo escolhida
RECUSADOO seu agenteNãoA descrição da ferramenta ou a instrução de sistema: o modelo não entendeu o contrato
FALHOUO serviçoTentouO serviço: fora do ar, regra de negócio, pedido inexistente

Misturar RECUSADO com FALHOU num único "erro" cega a operação. Uma alta de RECUSADO é problema de contrato, e se resolve com texto. Uma alta de FALHOU é problema de infraestrutura ou de regra de negócio, e se resolve com plantão. São dois times diferentes recebendo o alerta.

08 – Desfazer
24

Como se testa um agente sem modelo nenhum

Modelo é fonte de não determinismo: a mesma pergunta pode produzir saídas diferentes. Teste que depende disso é teste que falha de vez em quando, e teste que falha de vez em quando é ignorado pela equipe em duas semanas.

def test_alteracao_sem_cep_nao_chega_a_api(api, trilha):
    """O ponto da aula inteira: a chamada malformada não sai do agente."""
    Despachante(caminho_auditoria=trilha).despachar(
        "alterar_endereco_entrega", endereco_sem_cep())
    assert api.chamadas == []          # o dublê da API não recebeu nada

O que se testa sem modelo

Schema, Command, Despachante, auditoria e o laço. É onde mora a sua engenharia, e é 100% determinístico.

O que se testa com dublê

A API de Pedidos, substituída pela ApiFalsa do conftest.py. Nenhum socket é aberto na suíte.

O que sobra para a avaliação manual

Se o modelo escolhe a ferramenta certa. Isso é medição estatística, não teste de unidade.

Git Worktrees

Um repositório, vários diretórios de trabalho.
O que muda quando duas linhas de trabalho rodam ao mesmo tempo.

27

Dois agentes, um único diretório de trabalho [4]

A resposta em uma frase

O git checkout altera o único diretório de trabalho. Dois agentes no mesmo diretório é o mesmo que duas pessoas editando o mesmo arquivo sem saber uma da outra.

08 – O Problema do Checkout
28

"Então é só clonar duas vezes" [4]

Clonar de novo resolve o conflito de diretório e cria cinco problemas novos. Worktree resolve o conflito sem criar nenhum deles.

 Dois clonesDuas worktrees
HistóricoDuplicado em disco, e os dois divergemUm só, compartilhado
Commit feito de um ladoSó aparece no outro depois de push e fetchAparece imediatamente: é o mesmo repositório
Espaço em discoDuas cópias do .git inteiroUm .git, mais os arquivos de trabalho
Configuração, hooks e remotesConfigurar duas vezes, e manter em diaCompartilhados
Mesma branch aberta nos doisPermitido, e é onde o estrago começaO Git recusa: uma branch por worktree
O ponto que mais surpreende

Worktrees são mais seguras que clones. O Git impede, por desenho, que a mesma branch seja aberta em duas worktrees, e é exatamente esse o erro que dois agentes trabalhando em paralelo cometeriam.

08 – Worktree x Clone
29

Um repositório, vários diretórios de trabalho [4]

Por que isso resolve o slide anterior

Cada agente ganha o seu próprio diretório e o seu próprio HEAD, sem duplicar histórico. Nenhum git switch de um lado alcança os arquivos do outro.

08 – Como a Worktree Funciona
30

Os comandos que vocês vão usar hoje [4]

# criar um diretório de trabalho novo, ligado a uma branch que já existe
git worktree add ../wt-agente-pedidos agente/pedidos

# criar a branch e a worktree no mesmo comando
git worktree add -b agente/atendimento ../wt-agente-atendimento

# listar: caminho, commit e branch de cada diretório de trabalho
git worktree list

# remover quando terminar (a branch continua existindo)
git worktree remove ../wt-agente-pedidos

# limpar registros de worktrees cujo diretório foi apagado na mão
git worktree prune

A saída de git worktree list é estável e legível por máquina, ainda mais com --porcelain. É exatamente por ela que o verificar.py do laboratório confere o critério das duas worktrees, sem depender de vocês declararem nada.

08 – Comandos de Worktree
31

Quatro armadilhas de worktree [4]

1. Criar a worktree dentro do repositório

Ela vira um monte de arquivo não rastreado do próprio projeto, e o git status fica ilegível. Sempre um nível acima: ../wt-...

2. Tentar a mesma branch em duas worktrees

O Git recusa com already checked out. Não é limitação: é a proteção que evita duas escritas concorrentes na mesma linha de trabalho.

3. Apagar o diretório com rm -rf

O registro fica órfão em .git/worktrees e a listagem passa a mentir. Use git worktree remove, ou conserte depois com prune.

4. Esquecer que dependência não é compartilhada

Arquivo ignorado pelo Git não existe na worktree nova. node_modules, .venv e arquivos de ambiente precisam ser recriados em cada uma.

Por que isso é aula de agentes

Worktree é a técnica que torna viável rodar dois agentes ao mesmo tempo no mesmo projeto. Sem ela, "paralelizar com IA" termina em dois processos brigando pelos mesmos arquivos.

Passo 3 de 8: TODO-2, o schema da alteração

Seis campos obrigatórios, e o cep entre eles

Propriedades: pedido_id, logradouro, numero, cidade, uf, cep e complemento.

  • uf com pattern de duas letras maiúsculas; cep no formato 00000-000.
  • required com seis campos. complemento fica de fora: é opcional no contrato do serviço.
  • additionalProperties: False, para o modelo não contrabandear campo nenhum.

O cep em required é o que faz o passo 6 existir: sem ele aqui, a chamada malformada passa direto e chega ao serviço. Commit feat(passo-3): schema de alterar_endereco_entrega.

O que você acabou de provar: Você acabou de criar a condição da recusa. O cep em required é o único motivo pelo qual o passo 6 vai ter o que provar.

Vem pronto no --simular
