14 – O Desafio do Mini Mundo
5

Senha compartilhada entre serviços não resolve

Uma senha compartilhada entre os serviços

Um segredo no cabeçalho, o mesmo em todos os serviços, guardado em variável de ambiente.

  • Não diz quem é o usuário, só que alguém sabia a senha
  • Todo mundo que a tem pode tudo: não existe papel
  • Quando vazar, trocar significa reimplantar todos os serviços ao mesmo tempo
  • Não expira. O estagiário que saiu ano passado continua entrando
  • Não há trilha: o log registra a senha, não a pessoa

Um token assinado, por usuário, com prazo

Um provedor de identidade emite; cada serviço confere a assinatura com a chave pública.

  • Diz quem é, e o serviço registra isso no log
  • Carrega papéis: cliente não é motorista
  • Vaza um token e ele morre sozinho em 300 segundos
  • Revogar um usuário é desligá-lo em um lugar só
  • Nenhum serviço guarda segredo: só a chave pública
A pergunta que separa os dois

Segredo compartilhado responde "você sabe a senha?". Token assinado responde "quem é você, e o que você pode?". A segunda pergunta é a única que resolve a dor da LogiTech, porque a resposta muda conforme quem pergunta.

Dois tokens, dois propósitos

O access_token vai para as APIs: ele diz o que você pode. O id_token fica no cliente: ele diz quem você é, e é a parte que o OpenID Connect acrescentou ao OAuth. Mandar o id_token para a API é erro comum e recusa correta.

14 – A troca do código

OpenID Connect: a camada que faltava [3]

OAuth 2.0 sozinho

Responde "este portador pode acessar este recurso?".

Não define o formato do token, não define como descobrir onde fica o servidor, e não define como saber quem é o usuário. Cada fornecedor resolvia isso do seu jeito, e integrar dois era escrever dois adaptadores.

OIDC, por cima do OAuth

Acrescenta três coisas padronizadas:

  • id_token, um JWT sobre a identidade, com sub, nome e e-mail
  • o escopo openid, que é o que liga o OIDC
  • descoberta: um único endereço bem conhecido de onde sai toda a configuração
A frase para levar

OAuth 2.0 é autorização. OpenID Connect é autenticação, construída sobre ele. Quem diz "autenticar com OAuth" está, quase sempre, usando OIDC sem saber o nome.

Um token de verdade, decodificado

Token de exemplo da ana.cliente, no formato exato que o realm logitech emite. Os campos de tempo aqui são ilustrativos; o que foi medido no laboratório em 31/07/2026 está no rodapé do slide.

CABEÇALHO

{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "A2oKqrW2h5M4QILJ..."
}

O kid é o que permite trocar a chave sem derrubar ninguém: o token diz qual chave usar.

CONTEÚDO

{ "iss": "http://localhost:8090/realms/logitech",
  "sub": "b2c7...-...-...-...-...", "azp": "logitech-portal", "typ": "Bearer",
  "preferred_username": "ana.cliente",
  "iat": 1763564576, "exp": 1763564876,        // exp - iat = 300 segundos
  "realm_access":    { "roles": ["CLIENTE"] },  // <- daqui todo mundo le
  "resource_access": { }                        // <- vazio neste realm
}
Medido em 31/07/2026, no laboratório

exp - iat = 300 segundos, porque o realm fixa accessTokenLifespan: 300; o token tem 1266 caracteres; e resource_access vem vazio. Cinco minutos de janela: um token vazado morre sozinho antes de o suporte atender o chamado.

14 – JWKS
18

Duas armadilhas do JWT que biblioteca ruim ainda deixa passar

alg: none

O padrão prevê um JWT sem assinatura. O atacante monta o token que quiser, escreve "alg":"none" no cabeçalho e deixa a terceira parte vazia.

Uma biblioteca que obedece o campo alg do próprio token aceita: ela pergunta ao token qual algoritmo usar, e o token responde "nenhum".

Confusão de algoritmo

O JWKS é público: qualquer um baixa a chave pública. O atacante assina um token com HS256, usando a chave pública como segredo de HMAC.

Se o serviço decidir o algoritmo pelo token, ele pega a mesma chave pública e valida com sucesso. Assinatura confere, e o token é forjado.

A defesa é a mesma para os dois, e cabe em uma linha: quem decide o algoritmo é o servidor, não o token. O Jwt.java do laboratório recusa qualquer coisa que não seja RS256 antes de olhar mais nada, e o comentário no arquivo explica por quê.

14 – Armadilhas do JWT
19

Quiz de Verificação

Para que serve a assinatura de um JWT, e por que o backend pode confiar no payload sem consultar banco a cada requisição?
  • A A assinatura criptografa o payload, então só quem tem a chave consegue ler os dados do usuário.
  • B A assinatura garante integridade e autenticidade: se a chave pública do JWKS validar que ela foi gerada pela chave privada do provedor, o backend sabe que o payload não foi adulterado.
  • C A assinatura é um resumo do payload; o backend a compara com uma cópia guardada no banco de sessões.
  • D A assinatura contém a senha do usuário cifrada, e é por isso que o backend não precisa perguntar de novo.

Quiz de Verificação

Como o modelo RBAC organiza a autorização dos usuários no sistema?
  • A Cada usuário recebe uma lista própria de permissões, mantida no banco de cada serviço.
  • B As permissões são associadas a papéis, os papéis são atribuídos aos usuários, e o código só verifica se o usuário tem o papel exigido pelo recurso.

  • D Cada serviço mantém sua própria tabela de papéis, o que permite que o mesmo papel signifique coisas diferentes em cada um.

O realm é um arquivo, nunca vinte telas [9]

Configurar pela interface

  • Não entra no Git: não há o que revisar em pull request
  • Ninguém repete igual: cada aluno cria um realm um pouco diferente
  • Não sobrevive a docker compose down -v
  • Documentar vira captura de tela, que envelhece na próxima versão

--import-realm de um JSON versionado

  • Papéis, clients e usuários semeados são código
  • Mudança de política aparece no git diff
  • Ambiente reproduzível: um comando devolve tudo ao zero
  • A turma inteira tem exatamente o mesmo realm
keycloak:
  image: quay.io/keycloak/keycloak:26.0
  command: ["start-dev", "--import-realm", "--http-port=8090"]
  volumes:
    - ./keycloak:/opt/keycloak/data/import:ro     # o realm versionado entra aqui

Três coisas neste realm que não vão para produção, e o README diz isso com todas as letras: sslRequired: none, senha fraca e igual para os três usuários, e credencial escrita em arquivo versionado. Credencial de laboratório que parece de produção ensina a coisa errada.

14 – Git Worktrees II
34

Por que isto importa quando um agente escreve o código

O agente não espera

Um agente de IA refatorando a camada de segurança edita dezenas de arquivos em minutos. Se a interface está sendo mexida no mesmo diretório, os dois trabalhos se sobrepõem e o git status vira ruído.

Revisão separada por natureza

Mudança de autorização e mudança de tela têm risco diferente e revisor diferente. Duas branches, dois pull requests, duas conversas. Um PR único com as duas coisas não é revisado: é aprovado.

Teste contínuo dos dois lados

A suíte Java e o vitest em modo watch podem ficar rodando ao mesmo tempo, cada um no seu diretório, sem que um invalide o outro a cada troca de branch.

Voltar atrás fica barato

Se a frente de interface não fechar até as 22h30, ela simplesmente não é mesclada. A de segurança segue sozinha, porque nunca dependeu do diretório de trabalho da outra.

Onde as worktrees moram

Fora do repositório, um nível acima. Criadas dentro dele, viram arquivos não rastreados do próprio repositório e o git status fica ilegível. Desfazer é git worktree remove ../agent-auth.

O programa imprime o code_verifier, o code_challenge, a URL de autorização inteira, o código que voltou e o token decodificado em três partes. Leia a saída toda antes de seguir.

Preencha TAMANHO_DO_CODE_VERIFIER, CODE_CHALLENGE_METHOD, TOKEN_EXPIRA_EM_S, PAPEIS_NO_TOKEN, ISSUER_NO_TOKEN e RESOURCE_ACCESS_NO_TOKEN.

A próxima volta da espiral

Hoje a plataforma passou a saber quem está chamando. Isso não a torna segura: torna-a autenticada, que é outra coisa.

Aula 15, 10/11: o que um token válido ainda não impede

O assistente da LogiTech atende clientes autenticados e tem ferramenta que altera pedido. Um texto bem escrito dentro da pergunta pode fazer o modelo ignorar a instrução de sistema, e o token dele estará perfeitamente em ordem.

OWASP Top 10 para LLM, guardrails de entrada e saída, e Trivy nas imagens que sobem desde a Aula 03.

Aula 16, 17/11: os treze de pé, com um comando

A plataforma inteira sobe junto, autenticada de ponta a ponta, e o fluxo é validado do clique no portal até o banco, atravessando token, gateway e RAG. É o simulado da banca da Global Solution.

O contrato que vocês cumpriram hoje é exatamente o que será testado lá.

O que fica desta noite

Autenticação diz quem. Autorização diz o quê. Nenhuma das duas diz se o que o usuário pediu era uma boa ideia, e é aí que a Aula 15 começa.
