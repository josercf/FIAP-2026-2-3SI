Hoje não há conceito novo. Há operação.

O que muda

Até aqui cada aula acrescentou uma peça e a testou sozinha. Hoje as treze rodam ao mesmo tempo, na mesma rede, com a mesma identidade.

O que aparece só agora

Corrida de subida, healthcheck que mente, issuer que não bate, porta disputada. Nada disso existe quando se sobe um serviço por vez.

O que vocês levam

Um runbook: a sequência de perguntas que leva do sintoma à causa sem depender de sorte nem de reiniciar tudo.

Os seis defeitos que vamos ver aconteceram de verdade na construção deste acervo, entre março e julho de 2026. Cada um custou tempo de alguém. Nenhum é invenção didática, e é por isso que estão aqui.

Takeaway

Integração não é a soma das partes: é a categoria de problema que só existe quando as partes se encontram.

16 – O que o --wait espera

O runbook: quatro comandos, nesta ordem

# 1. Quem subiu, quem esta healthy, quem saiu. O `-a` inclui os que ja morreram.
docker compose ps -a

# 2. O que o processo disse antes de morrer. Sem `--tail` voce le a subida inteira.
docker compose logs --tail 50 <servico>

# 3. O que o HEALTHCHECK respondeu, e nao o que voce acha que ele responde.
#    O campo `Output` traz a saida crua do comando. E aqui que "Connection
#    refused" com o servico no ar aparece, e e a pista que resolve a FALHA-1.
docker inspect --format '{{json .State.Health}}' logitech-<servico>-1 | python3 -m json.tool

# 4. Um servico enxerga o outro pela rede da plataforma? Isto separa
#    "DNS do Compose" de "porta errada" de "o servico esta fora do ar".
docker compose exec pedidos wget -qO- http://frete:8000/health
A regra do runbook

Nunca reinicie antes do passo 3. Reiniciar apaga a evidência e transforma um defeito reproduzível em intermitente, que é a categoria mais cara de todas.

Falha 1: o healthcheck que resolve para o lugar errado [6]

16 – Falha 1: IPv6
15

A mesma linha errada, dois desfechos

O docker-compose.yml de hoje traz localhost em dois healthchecks. Só um dos dois falha.

frete, em Python

O uvicorn faz bind em 0.0.0.0, que é só IPv4. A conexão em ::1 é recusada.

Resultado medido: unhealthy permanente.

notificacoes, em Node

O servidor HTTP do Node faz bind em ::, que aceita conexão IPv4 mapeada. A mesma linha errada funciona.

Resultado medido: healthy.

# medido em 31/07/2026, de dentro do container de notificacoes
$ docker compose exec notificacoes node -e "..."
address: {"address":"::","family":"IPv6","port":9999}
Takeaway

Corrija os dois. Defeito que só não aparece porque a stack ao lado é tolerante não é defeito corrigido: é defeito esperando outra imagem base, outra versão do runtime ou outro sistema operacional.

Falha 3: a porta ocupada, e a mensagem que culpa o inocente

19

Falha 5: Exited (0), sem erro nenhum no log

$ docker compose ps -a
NAME                      STATUS
logitech-mcp-logitech-1   Exited (0) 9 seconds ago      <- saiu com SUCESSO

$ docker compose logs mcp-logitech
[mcp-logitech] no ar por stdio. rag=http://rag:8010 pedidos=http://pedidos:8080
                                                    # e mais nada.

Por que zero, e não um

Do ponto de vista do processo, terminar de ler a entrada padrão é o fim normal do trabalho. Ele não travou nem estourou: acabou. Log limpo e código de saída zero são o relato honesto disso.

O que faltava

Uma linha: stdin_open: true, equivalente ao -i do docker run. Ela mantém a entrada padrão aberta, e o servidor MCP fica esperando a próxima mensagem JSON-RPC em vez de receber EOF.

Takeaway

Um serviço que não fala HTTP tem um ciclo de vida diferente, e o Compose não adivinha isso. Quem escolhe o transporte assume as consequências dele na orquestração.

16 – Falha 5: stdio
20

Falha 6: a plataforma sobe inteira e não protege nada

A ADR-009 criou LOGITECH_AUTH_ATIVA com padrão false, para que os laboratórios das Aulas 05 a 12 continuassem passando depois que a segurança entrou. Esquecer de ligá-la não produz erro nenhum.

# o sintoma: nao ha sintoma. Tudo fica verde.
$ docker compose ps           # 13 de 13 healthy
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/api/v1/pedidos
200                           # SEM TOKEN NENHUM

# a confirmacao: todo servico anuncia o proprio interruptor no /health
$ curl -s http://localhost:8080/health | python3 -m json.tool
{ "status": "ok", "servico": "pedidos", "auth_ativa": false }

Isto não é porta dos fundos escondida: está declarada no README, aparece no slide, e o verificador exige que ela esteja ligada para dar o critério por cumprido. Sem esse interruptor, ligar segurança teria quebrado retroativamente quatro laboratórios já publicados.

Takeaway

Defeito silencioso é o mais caro: não há log para ler, não há container vermelho para olhar. Contra ele, só serve verificação ativa, e é por isso que o critério é um `curl` sem token esperando 401.

16 – Falha 6: o interruptor
21

O recurso que o Compose usa mas não cria

networks:
  logitech-net:
    external: true          # criada a mao na Aula 03, com `docker network create`

volumes:
  logitech-telemetria:
    external: true          # tambem herdada da Aula 03
  logitech-postgres:
    name: logitech-postgres # esta nasce aqui, e quem a destroi e o Compose

Por que é deliberado

É o reencontro com o que vocês criaram por comando na Aula 03: o orquestrador referencia o recurso, não o recria, e não o apaga no down. As duas formas convivem no mesmo arquivo, de propósito.

O sintoma quando falta

O up falha antes de criar qualquer container, com uma mensagem que não diz "crie a rede". Nenhum log de serviço ajuda, porque nenhum serviço chegou a subir.

docker network create logitech-net
docker volume create logitech-telemetria

Takeaway

`external: true` transfere a responsabilidade de existir para fora do arquivo. É a decisão certa quando o recurso é anterior ao projeto, e é o primeiro lugar a olhar quando o `up` morre sem subir nada.

Por que essa ordem, e não outra

Sobe primeiro

É a única afirmação que não dá para fazer no slide. Deixar para o fim é como fica quem não ensaiou: acaba o tempo com o build rodando.

Fluxo feliz antes do de erro

Mostrar o 403 antes do 201 faz parecer que algo quebrou. Mostrar os dois na ordem faz parecer o que é: controle de acesso funcionando.

A régua no fim

O verificar.py verde fecha a apresentação com evidência, e não com opinião. É o argumento que não depende de convencer ninguém.

Uma autocrítica

Grupo que só elogia o próprio projeto parece que não entendeu o projeto. Uma decisão que tomariam diferente, com o motivo, é o item que mais separa apresentação boa de apresentação decorada.

Takeaway

A ordem da demonstração é uma decisão de projeto como qualquer outra: ela tem motivo, e o motivo é o que a banca consegue acompanhar em dez minutos.

O que a banca vê, mesmo sem vocês dizerem

O README

Se ele sobe a plataforma do zero na mão de quem nunca viu o projeto. Testem entregando o README a outro grupo e olhando em silêncio.

O histórico do Git

Se há mais de uma pessoa commitando, e se as mensagens dizem o que mudou. Trinta commits chamados "ajustes" contam uma história.

A distância entre a tela e o repositório

Se o que está rodando é o que está commitado. Um git status limpo antes de começar resolve isso.

A resposta a "por que assim?"

Se vem um motivo ou um encolher de ombros. As ADRs do semestre existem para essa pergunta ter resposta escrita.

Takeaway

A apresentação começa antes de vocês falarem. Metade do que a banca conclui já está no repositório.
